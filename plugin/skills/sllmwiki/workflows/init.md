# init: set up a wiki repository

A wiki is a git repository of its own. Run this in the repository that will hold it.

1. **Get the tools ready.** Preflight (`SKILL.md`) has offered to install what's required. On a first setup, when it warned about `gh`, add setting it up to step 3's questions (default: no), since the wiki's remote and its pull requests go through `gh`. On a yes, install it the same way, then the owner signs in with `! gh auth login`, or `! gh auth refresh -h github.com -s workflow` when it says the token lacks that scope. On a no, carry on: runs print the link to open each pull request instead.
2. **A rerun on a wiki** (it has `sllmwiki/tags/tags.yaml`) is a run like any other, one pull request: start it with `publish.py start init-refresh --title "Bring the wiki up to date" --prompt "<the user's request, verbatim>"`. When `start` refuses because the tree isn't clean, name the files to the owner and stop; never commit or move them.
3. **Ask the owner's preferences** before writing anything. `init.py --ask --json` lists the settings to ask about, each with its current value and what it means: every one on a first setup; on a rerun, only those the plugin added since (none: skip this step). Ask them in one go, grouped: the narratives' language; the source policy; the book's formats, title and author; Obsidian; markers and generated figures; who never to list as an SME, such as the owner. Offer each one's value as the default, and don't ask again what the request already said.
4. Run `init.py --name <repository name>`, with `--set KEY=VALUE` for each answer that differs from its value (a list comma-separated: `--set smes_exclude=@ann,dependabot`). When it reports files that aren't a wiki's, tell the owner which, and ask whether to set the wiki up here anyway or in a new, empty repository. Pass `--force` only on their yes.
5. If the repository has no remote, offer to create one on GitHub (`gh repo create <name> --private --source . --push`), private unless the owner says otherwise; a public wiki keeps copies of openly licensed sources only.
6. If it has a remote, check that the local default branch matches the remote's (`git fetch` and compare); stop and tell the owner if it has diverged.
7. Commit:
   - **First setup:** `init.py --commit --prompt "<the user's request, verbatim>"`, which stages only what it wrote, then push the default branch if there's a remote.
   - **A rerun:** `publish.py summary init --json '{...}'` with what changed, `publish.py commit init --subject "Bring the wiki up to date"` and `publish.py pr`. Never push the default branch.
8. Reply with what was created or updated, then a short tour of what comes next: ask with `/sllmwiki:query "<a question>"`; grow the wiki with `/sllmwiki:build "<a first question>"`, which opens a pull request to review and merge; publish it as a book with `/sllmwiki:release`. Say that `sllmwiki/Config.toml` holds the answers and the other settings, to change any time. If `init.py` couldn't write `.claude/settings.json` (a sandbox guards it), give the owner the two keys from the skill's `templates/wiki/.claude/settings.json` to merge in by hand, so the team's agents load the plugin.

Rerun after a plugin update: it refreshes the files it owns and keeps the wiki's own.
