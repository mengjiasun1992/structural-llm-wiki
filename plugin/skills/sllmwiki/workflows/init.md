# init: set up a wiki repository

A wiki is a git repository of its own. Run this in the repository that will hold it.

1. **Offer an upgrade.** `sllmwiki doctor --updates` asks PyPI for the latest release. When it reports a newer one, tell the owner which version they're on and which is out, and offer to upgrade: on a yes, run the command it prints, then ask them to restart Claude Code and rerun `/sllmwiki:init`, which then uses the new version and brings the wiki up to it; on a no, or when PyPI can't be asked, carry on with this one.
2. **Sign in to `gh`.** `sllmwiki doctor` (`SKILL.md`) has installed the missing tools. On a first setup, when `gh` isn't signed in, or its token lacks the workflow scope, ask the owner to run `! gh auth login` (or `! gh auth refresh -h github.com -s workflow`), since the wiki's remote and its pull requests go through it; if they'd rather not, carry on: runs print the link to open each pull request instead.
3. **A rerun on a wiki** (it has `sllmwiki/tags/tags.yaml`) is a run like any other, one pull request: start it with `sllmwiki publish start init-refresh --title "Bring the wiki up to date" --prompt "<the user's request, verbatim>"`. When `start` refuses because the tree isn't clean, name the files to the owner and stop; never commit or move them.
4. **Ask the owner's preferences** before writing anything. `sllmwiki init --ask --json` lists the settings to ask about, each with its current value and what it means: every one on a first setup; on a rerun, only those the plugin added since (none: skip this step). Ask them in one go, grouped: the narratives' language; the source policy; the book's formats, title and author; Obsidian; markers and generated figures; who never to list as an SME, such as the owner. Offer each one's value as the default and, where it lists `choices`, those as the options (a language without a pack can still be typed in), and don't ask again what the request already said.
5. Run `sllmwiki init --name <repository name>`, with `--set KEY=VALUE` for each answer that differs from its value (a list comma-separated: `--set smes_exclude=@ann,dependabot`). When it reports files that aren't a wiki's, tell the owner which, and ask whether to set the wiki up here anyway or in a new, empty repository. Pass `--force` only on their yes.
6. If the repository has no remote, offer to create one on GitHub (`gh repo create <name> --private --source . --push`), private unless the owner says otherwise; a public wiki keeps copies of openly licensed sources only.
7. If it has a remote, check that the local default branch matches the remote's (`git fetch` and compare); stop and tell the owner if it has diverged.
8. Commit:
   - **First setup:** `sllmwiki init --commit --prompt "<the user's request, verbatim>"`, which stages only what it wrote, then push the default branch if there's a remote.
   - **A rerun:** `sllmwiki publish summary init --json '{...}'` with what changed, `sllmwiki publish commit init --subject "Bring the wiki up to date"` and `sllmwiki publish pr`. Never push the default branch.
9. Reply with what was created or updated, then a short tour of what comes next: ask with `/sllmwiki:query "<a question>"`; grow the wiki with `/sllmwiki:build "<a first question>"`, which opens a pull request to review and merge; publish it as a book with `/sllmwiki:release`. Say that `sllmwiki/Config.toml` holds the answers and the other settings, to change any time. If `sllmwiki init` couldn't write `.claude/settings.json` (a sandbox guards it), give the owner the keys it printed to merge in by hand, so the team's agents load the plugin.

Rerun after a plugin update: it refreshes the files it owns and keeps the wiki's own.
